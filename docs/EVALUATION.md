# CareerPilot AI — Evaluation & Quality Engineering Strategy

- **Статус:** Draft v1.0 (Stage 0 — проектирование).
- **Связанные:** [AI_DESIGN.md](AI_DESIGN.md) · [ARCHITECTURE.md](ARCHITECTURE.md) · [DATABASE.md](DATABASE.md)
- **Правило Stage 0:** все численные целевые значения — **гипотезы**, пока не подтверждены реальными измерениями на собственных датасетах.

---

## 1. Принципы

1. **Evaluation с первого спринта AI-функции.** Функция считается сделанной, только если есть: golden-датасет, автоматический прогон, зафиксированный baseline.
2. **Датасеты — код.** Каноническое хранение golden-наборов: git (JSONL + скрипты сборки). БД (`evaluation_*`) — реестр прогонов; Langfuse datasets — зеркало для ручных экспериментов. Всё воспроизводимо из репозитория.
3. **Детерминизм, где возможно.** Метрики считаются кодом (совпадение множеств, ранжирование). LLM-as-judge — только там, где без него нельзя (связность текста), с калибровкой против человеческой разметки.
4. **Regression gates.** Изменение промпта/модели/логики без прогона evaluation — запрещено процессом (CI-гейт + чек-лист ревью).
5. **Разделение уровней тестов.** Быстрые обязательные (unit/integration/contract) — на каждый PR; AI evaluation — по требованию + nightly; e2e — перед релизом.

## 2. Пирамида тестов

| Уровень | Что покрывает | Инструменты | Когда запускается |
|---|---|---|---|
| **Unit** | Чистые функции: нормализация текста, fingerprint, evidence binding, компоненты скора, hard filters, конечные автоматы статусов, маскирование PII | pytest, hypothesis (property-based для нормализаторов) | каждый PR, обязателен |
| **Integration** | Репозитории + PostgreSQL (testcontainers), outbox/диспетчер, Celery-таски (eager), S3 (minio), LangGraph граф с мок-LLM (state transitions, interrupt/resume) | pytest + testcontainers | каждый PR, обязателен |
| **Contract** | OpenAPI-схема (schemathesis на auth/валидацию), изоляция тенантов по всем поверхностям: API (запрос чужого id → 404), фоновые задачи (вызов Celery-таски с чужим `user_id` → guard no-op, без записи и без утечки данных), graph runs (`copilot resume` чужого run/application → 404), документы и файлы (presigned на чужой объект → 404 до выдачи URL); контракт Source Adapter (фикстуры сырых ответов источников) | schemathesis, pytest | каждый PR, обязателен |
| **AI evaluation** | Все LLM-компоненты на golden-датасетах (§4) | собственный harness (`make eval`), Langfuse для трейсов | PR с изменением промпта/модели — обязательный локальный прогон; nightly по main |
| **E2E** | Ключевые пользовательские потоки UJ-1..UJ-4 в staging-окружении с реальной БД и мок-LLM (recorded responses); обязательный кейс — рендеринг недоверенного HTML из вакансии (санитизация не пропускает скрипты) | Playwright | перед релизом stage |
| **Regression (AI)** | Сравнение с baseline: метрики не хуже порогов; diff-отчёт по кейсам | harness + `evaluation_runs` | тот же триггер, что AI evaluation |

Мок-LLM слой: `LLMClient` подменяется записанными golden-ответами (кассеты) — интеграционные тесты детерминированы и бесплатны; кассеты обновляются при смене промпта вместе с evaluation-прогоном.

## 3. Метрики по доменам

### 3.1 Resume extraction (Profile Analyzer)

| Метрика | Формула / определение | Цель-гипотеза |
|---|---|---|
| Precision (факты) | верно извлечённые / все извлечённые | ≥ 0.95 |
| Recall (факты) | верно извлечённые / все в golden-разметке | ≥ 0.85 |
| F1 | гармоническое P/R | ≥ 0.90 |
| Date accuracy | доля корректно распознанных периодов (±1 месяц, корректные границы) | ≥ 0.90 |
| Unsupported facts rate | доля фактов без валидной цитаты (после evidence binding) | 0 (жёстко: механический отсев) |
| Skill normalization accuracy | доля корректных маппингов на справочник (разметка) | ≥ 0.90 |

Golden-датасет: ≥ 20 резюме (RU/EN; PDF/DOCX; разные макеты: ATS-friendly и «дизайнерские»; 2–3 намеренно сложных: таблицы, два столбца, скан — сканы помечены как ожидаемая ошибка). Разметка: факты + границы цитат. Пополнение: каждое резюме владельца, вычитанное вручную, — кандидат в набор.

### 3.2 Job retrieval (гибридный поиск кандидатов)

| Метрика | Определение | Цель-гипотеза |
|---|---|---|
| Recall@10 | доля релевантных, попавших в топ-10 | ≥ 0.70 |
| Precision@10 | доля релевантных в топ-10 | ≥ 0.60 |
| MRR@10 | средний обратный ранг первой релевантной | ≥ 0.65 |
| nDCG@10 | ранжирование с учётом градаций релевантности | ≥ 0.65 |

Golden-датасет: ≥ 200 вакансий (смесь AI/LLM/frontend/нерелевантных, RU/EN) с разметкой релевантности профилю-эталону (3 уровня: 2=сильный матч, 1=смежный, 0=нерелевантен) + 20+ поисковых запросов. Сбор: из источников Stage 3 вручную размечается владельцем; дубликаты в наборе — отдельно помечены (используется и для тестов дедупа).

### 3.3 Job matching

| Метрика | Определение | Цель-гипотеза |
|---|---|---|
| Precision@5 | доля действительно релевантных в топ-5 по скору | ≥ 0.80 |
| nDCG@10 | качество ранжирования против разметки | ≥ 0.70 |
| False Positive Rate | доля вакансий с высоким скором, но нарушенным обязательным ограничением / нерелевантных | ≤ 0.10 |
| Hard filter correctness | точность детерминированного применения фильтров (unit + golden cases) | 1.00 (детерминированная функция) |
| Human agreement (κ) | согласие скора с решением человека (interested/dismissed), Cohen's kappa | ≥ 0.60 |
| Explanation faithfulness | доля объяснений, где вердикт действительно следует из указанных fact_ids (аудит выборки) | ≥ 0.95 |

Human agreement: считаем на живых данных — решения пользователя (`job_matches.decision`) копятся автоматически; раз в этап — пересчёт κ и ревизия порогов/весов.

### 3.4 Application generation (Copilot)

| Метрика | Определение | Цель-гипотеза | Инструмент |
|---|---|---|---|
| Factual consistency | доля утверждений документов, верифицированных фактами профиля | ≥ 0.95 | fact_checker (автоматически, LLM+code) + выборочный аудит человеком |
| Unsupported claims rate | доля утверждений без подтверждения (после fact check, финальные версии) | ≤ 0.03 | fact_checker |
| Requirement coverage | доля обязательных требований вакансии, адресованных в адаптированном резюме | ≥ 0.85 | код: сопоставление с `requirements_must` (по фактам/терминам) |
| Answer relevance | уместность/качество ответов на вопросы | оценка LLM-judge 1–5 + калибровка | ≥ 4.0 средний, κ с человеком ≥ 0.5 |
| Human acceptance rate | доля документов, одобренных без существенных правок | ≥ 0.70 | живая метрика (review flow) |

LLM-as-judge правила: judge-модель ≠ рабочая модель задачи; промпт judge-а с rubric и примерами; каждый judge-кейс хранит trace; калибровка judge против разметки человека (≥ 50 кейсов) перед доверием; judge-скор никогда не единственный аргумент решения.

## 4. Датасеты: каталог

| Набор | Формат | Размер (старт) | Наполнение |
|---|---|---|---|
| `resume_extraction` | JSONL: `{file, facts[], expected}` | 20 | резюме + ручная разметка |
| `job_normalization` | JSONL: `{raw_payload, expected_draft}` | 100 (по источникам) | фикстуры реальных ответов источников |
| `job_dedup` | JSONL: группы дублей/не-дублей | 50 групп | ручная разметка |
| `job_retrieval` | JSONL: вакансии с relevance + запросы | 200 вакансий, 20 запросов | Stage 3, размечает владелец |
| `job_matching` | JSONL: `{profile_snapshot, job, expected_verdicts}` | 100 | из retrieval-набора + вердикты |
| `generation` | JSONL: `{profile, job, questions, expected_assertions, style}` | 30 | ручная сборка; assertions = что обязано/запрещено появиться |
| `prompt_injection` | JSONL: вакансии с инъекциями + ожидаемое поведение | 20 | adversarial set: инъекции через описания вакансий **и через загружаемые документы**; кейсы на подмешивание HTML/скриптов в генерацию (ожидание — контент экранирован при рендеринге, [SECURITY.md](SECURITY.md) §6.2, §7) |

Хранение: `backend/tests/eval/datasets/*.jsonl` + генераторы; регистрация в `evaluation_datasets`.

## 5. Процесс: эксперимент → решение

```
изменение (промпт/модель/веса) 
  → make eval --suite <suite> --compare baseline
  → evaluation_run (config: модели, версии промптов, git_sha; metrics; case_results)
  → diff-отчёт: метрики в целом + регрессии по кейсам
  → гейт: нет метрики ниже порога (baseline − ε), иначе блок
  → обновление baseline-файла в PR (reviewable)
```

- Baseline-пороги живут в git (`eval/baselines.json`) — изменение порогов = осознанный PR.
- Прогоны дорогих сюитов (generation) можно ограничивать сэмплированием на PR и полным — nightly.
- Langfuse: трейсы каждого прогона ссылаются на `evaluation_run.id` — можно спускаться до конкретного LLM-вызова в провальном кейсе.

## 6. Живые (production) метрики качества

- Human acceptance rate (одобрения документов), decisions по матчам (interested/dismissed) — источники для human agreement.
- Ошибки fact_checker'а, найденные пользователем при ревью (кнопка «неверная генерация» с причиной) — канал adverse feedback в датасеты.
- Доля вакансий, закрытых между циклами recheck (свежесть), — качество verification.
- Latency/cost из `ai_invocations` против бюджетов ([AI_DESIGN.md §7](AI_DESIGN.md)).

## 7. CI (GitHub Actions) — карта гейтов

| Workflow | Триггер | Шаги |
|---|---|---|
| `ci.yml` | PR | ruff + mypy → unit → integration (testcontainers) → contract (schemathesis smoke) → openapi-diff (breaking changes API) |
| `eval.yml` | PR с `ai/**` изменениями / nightly | вычисление кассет → eval suites (детерминированные части) → report в PR-комментарий; полные сюиты nightly на main |
| `release.yml` | тег | e2e (Playwright, staging) → build & push образов |

Обязательные PR-гейты: lint, unit, integration, contract, openapi-diff. AI eval — обязательный при изменении промптов/моделей (path-filter), иначе nightly.

## 8. Известные ограничения стратегии

- Датасеты малы на старте (владелец один) — доверенные интервалы широкие; метрики читаются как тренды, не абсолюты; растут с использованием продукта.
- LLM-judge не заменяет human review продуктовых текстов — только фильтр.
- Retrieval-метрики зависят от пула вакансий датасета; при подключении новых источников набор расширяется (иначе оценка смещена).
- Скрытые регрессии стиля (тон, структура письма) без judge/человека не ловятся — принимается.
