## 1. Обзор продукта

### 1.1 Проблема

Поиск работы в AI/LLM-направлении — это конвейер рутинных операций:

1. Вакансии разбросаны по множеству площадок, форматы несовместимы, объявления дублируются и устаревают.
2. Ручное сопоставление требований вакансии со своим опытом занимает 15–40 минут на вакансию.
3. Адаптация резюме и написание cover letter под каждую вакансию — трудоёмко, а качество откликов напрямую влияет на конверсию в интервью.
4. Отклики нигде не фиксируются: нет истории, статусов и напоминаний о follow-up.

### 1.2 Видение

**CareerPilot AI** — персональный AI Career Assistant, который:

- агрегирует вакансии из нескольких **разрешённых** источников и приводит их к единому формату;
- ведёт структурированный, **верифицированный пользователем** Career Profile на основе загруженных резюме;
- оценивает соответствие профиля требованиям вакансии с **объяснимым скором** и списком пробелов;
- готовит материалы отклика (адаптированное резюме, cover letter, ответы на вопросы работодателя) с **гарантией фактической достоверности**;
- управляет воронкой откликов и уведомляет через Telegram.

### 1.3 Ключевой принцип: Prepare, not Send

Система **готовит** материалы отклика, но **не отправляет** их. Пользователь всегда проверяет результат и отправляет отклик самостоятельно. Это осознанное продуктовое ограничение (см. [DECISIONS.md, ADR-008](DECISIONS.md)):

- этическое: пользователь сохраняет контроль над тем, что отправляется от его имени;
- юридическое: исключает риск нарушения правил площадок о массовом автоотклике;
- качественное: human review — обязательный контур контроля фактической достоверности.

### 1.4 Формат продукта

- **Web Dashboard** — основной интерфейс (управление профилем, вакансиями, откликами).
- **Telegram Bot** — уведомления и лёгкие взаимодействия (обзор новых матчей, напоминания).

### 1.5 Целевая аудитория

| Сегмент | Описание | Горизонт |
|---|---|---|
| Владелец (primary persona) | Senior-инженер (AI Engineer / Senior Frontend с AI/LLM Integration), ищущий роли AI Engineer, LLM Engineer, AI Application Engineer и смежные | MVP |
| Релоканты и удалёнщики RU/EU рынка | Те же роли, критичны фильтры по локации, зарплатной вилке, визовой поддержке | Ближайшее будущее |
| Широкая аудитория соискателей | Multi-user SaaS | Отложено; архитектура готовится |

Персона владельца задаёт приоритеты MVP: роли AI/LLM, рынки RU + международный remote, двуязычность документов (RU/EN).

## 2. Цели и анти-цели

### 2.1 Цели MVP

- G-1. Один загруженный резюме-файл превращается в структурированный, подтверждённый пользователем Career Profile с указанием источника каждого факта.
- G-2. Вакансии из ≥2 разрешённых источников собираются, нормализуются, дедуплицируются и проверяются на актуальность.
- G-3. Каждая вакансия получает объяснимый match score с привязкой к требованиям вакансии и фактам профиля; обязательные ограничения пользователя (hard filters) не могут быть «перекрыты» высокой семантической оценкой.
- G-4. Для выбранной вакансии система генерирует адаптированное резюме, cover letter и ответы на типовые вопросы работодателя; все утверждения проверяются на соответствие фактам профиля.
- G-5. Пользователь управляет воронкой откликов и получает уведомления в Telegram.
- G-6. Качество всех AI-компонентов измеряется на датасетах с первого спринта разработки (см. [EVALUATION.md](EVALUATION.md)).

### 2.2 Анти-цели (Out of Scope)

| # | Что не делаем | Причина |
|---|---|---|
| NG-1 | Автоматическая отправка откликов | Принцип Prepare, not Send (ADR-008) |
| NG-2 | Browser automation, scraping, обход CAPTCHA/авторизации | Правила площадок; ADR-009 |
| NG-3 | Массовый парсинг LinkedIn/Indeed/Wellfound/Работа.ру без официального API | Требует проверки ToS; на текущий момент публичных разрешённых API нет (см. [INTEGRATIONS.md](INTEGRATIONS.md)) |
| NG-4 | Написание резюме «с нуля» и выдумывание опыта | Генерация допустима только на основе подтверждённых фактов |
| NG-5 | Подготовка к интервью (mock interviews) в MVP | Возможно в будущем |
| NG-6 | Мобильные приложения | Достаточно responsive web + Telegram |
| NG-7 | Биллинг в MVP | Subscription & Usage — архитектурно, реализация позже |

## 3. Пользовательские сценарии (User Journeys)

### UJ-1. Первичная настройка профиля

**Актор:** пользователь (владелец).
**Триггер:** первый вход в Web Dashboard.
**Шаги:**

1. Регистрация (email + пароль).
2. Загрузка резюме (PDF/DOCX). Файл сохраняется в приватное хранилище; запускается асинхронный разбор.
3. В течение ~1–3 минут система извлекает факты: навыки, места работы, должности, длительности, проекты, образование, достижения, языки.
4. Экран «Обзор фактов»: каждый факт показан с цитатой-подтверждением из резюме, confidence и статусом. Пользователь подтверждает, редактирует, отклоняет факты или добавляет свои.
5. Заполнение Career Profile: целевые должности, грейд, зарплатная вилка, локации, формат работы (remote/hybrid/onsite), тип занятости, hard filters (например: «только remote», «не рассматриваю компании X, Y», «нужна визовая поддержка»).
6. Профиль активирован — можно создавать поиски вакансий.

**Результат:** подтверждённый набор фактов (`profile_facts` со status=confirmed) и активный `career_profile`.

**Критерии приёмки:**
- ни один факт не появляется без цитаты из исходного резюме либо пометки «добавлено пользователем»;
- этап 3 асинхронный: UI показывает статус и не блокируется;
- повторная загрузка резюме добавляет факты, не удаляя ранее подтверждённые.

### UJ-2. Настройка поиска и сбор вакансий

1. Пользователь создаёт Job Search: ключевые слова (например, "AI Engineer", "LLM Engineer"), локации, источник(и).
2. По расписанию и по кнопке «Запустить сейчас» система опрашивает источники разрешёнными способами (API/RSS), соблюдая rate limits.
3. Сырые объявления нормализуются к единой схеме, дедуплицируются (одно объявление на нескольких площадках → одна каноническая вакансия со ссылками на все копии).
4. Актуальность проверяется повторным обращением к источнику: закрытые/исчезнувшие вакансии получают статус `closed`/`gone`.
5. Dashboard: лента вакансий с фильтрами и сортировкой по match score.

**Критерии приёмки:**
- дубликаты не создают отдельных карточек; у вакансии видны все источники;
- вакансия, закрытая на источнике, помечается не позднее N часов (N — гипотеза: 24 ч для активных в поиске);
- ошибки источника не останавливают обработку других источников (изоляция сбоев).

### UJ-3. Матчинг и объяснение

1. Для новой канонической вакансии запускается Job Matching.
2. Проверяются hard filters. Нарушение → вакансия помечается «не соответствует обязательным условиям», score не компенсирует.
3. Гибридный поиск (лексический + семантический) и реранкинг формируют итоговый скор.
4. Пользователь открывает вакансию и видит:
   - общий скор и его разложение (hard filters / навыки / опыт / локация / зарплата / семантика);
   - какие требования закрыты какими фактами профиля (с цитатами);
   - список недостающих навыков (skill gaps) с разделением на критичные/желательные;
   - вердикт: «Сильный матч / Стоит попробовать / Матов мало».

**Критерии приёмки:**
- каждое объяснение ссылается на конкретное требование вакансии и конкретный факт профиля (идентификаторы);
- нарушение hard filter видимо явным списком нарушенных ограничений.

### UJ-4. Подготовка отклика (Application Copilot)

1. Пользователь выбирает вакансию и нажимает «Подготовить отклик». Создаётся Application и запускается LangGraph-workflow (см. [AI_DESIGN.md](AI_DESIGN.md)).
2. Система анализирует вакансию, сопоставляет с профилем, определяет пробелы.
3. Если для сильного отклика не хватает информации (например, «есть ли у вас опыт с RAG в production?»), workflow **приостанавливается** и задаёт вопрос пользователю (в Dashboard и/или Telegram). Пользователь отвечает; workflow продолжается. Пропуск вопросов допустим.
4. Генерируются: адаптированное резюме, cover letter, ответы на вопросы из вакансии. Все документы — версии, предыдущие версии сохраняются.
5. Fact checker прогоняет утверждения документов по подтверждённым фактам профиля; спорные утверждения подсвечиваются.
6. Пользователь просматривает, редактирует (правки сохраняются как пользовательские версии), одобряет или запрашивает перегенерацию с комментарием.
7. Одобренные материалы фиксируются в Application. Пользователь **самостоятельно** скачивает документы и отправляет отклик на площадке.

**Критерии приёмки:**
- workflow переживает перезапуск процесса (checkpointing), ожидание ответа пользователя неограничено по времени;
- каждое сгенерированное утверждение либо подтверждено фактом, либо явно помечено как «непроверено»;
- в документах нет опыта/навыков, отсутствующих в профиле (проверяется автоматически);
- история версий документов доступна и откатываема.

### UJ-5. Воронка откликов и отслеживание

1. После ручной отправки отклика пользователь отмечает статус: `submitted`.
2. Дashboard показывает воронку (интерес → отправлено → интервью → оффер/отказ) и напоминания: «нет ответа 7 дней — стоит follow-up».
3. Все переходы статусов логируются; карточка отклика содержит вакансию, материалы, историю.

### UJ-6. Уведомления

1. Пользователь привязывает Telegram: генерируется одноразовый код → отправляется боту → аккаунт связан.
2. Управление подписками: новые матчи выше порога, «материалы готовы», напоминания о follow-up, дайджест (ежедневно/еженедельно).
3. Уведомления содержат ссылку на соответствующий экран Dashboard.

## 5. Нефункциональные требования

| ID | Категория | Требование | Целевое значение (гипотеза до измерений) |

## 7. Допущения, ограничения и риски продукта

### 7.1 Допущения

- A-1. Основной язык вакансий: русский и английский; таргетные роли — AI/LLM-инженерия и смежные.
- A-2. Объём вакансий для личного использования: единицы тысяч активных записей — PostgreSQL + pgvector достаточны без выделенной векторной БД.
- A-3. Пользователь честно подтверждает факты профиля; система не занимается детекцией обмана резюме.
- A-4. Telegram — основной канал уведомлений.

### 7.2 Ограничения

- C-1. Отправка откликов всегда ручная (NG-1).
- C-2. Источники вакансий — только с официальным разрешённым доступом (см. [INTEGRATIONS.md](INTEGRATIONS.md)).
- C-3. MVP — single-user деплой (владелец), но схема данных и изоляция — multi-user с первого дня.

### 7.3 Риски

| Риск | Вероятность | Влияние | Митигция |
|---|---|---|---|
| R-1. Нет бесплатного официального доступа к hh.ru API (подтверждено: публичный поиск закрыт с апреля 2026, доступ — платная услуга «Доступ к API hh») | высокий | RU-рынок недоступен через hh.ru в MVP | Опираться на бесплатные официальные API (Arbeitnow, Remotive, Adzuna, HN Algolia) + ATS-борды компаний; решение о платном доступе к hh.ru — отдельное решение владельца |
| R-2. ToS ATS-бордов/карьерных страниц ограничивают автоматический сбор | средний | сужение пула источников | Ручная проверка ToS per-source, robots.txt, кэширование, низкая частота опроса |
| R-3. Качество LLM-извлечения фактов недостаточно без ручной вычитки | средний | доверие к матчингу | Обязательный human confirmation; evaluation-датасеты; confidence gating |
| R-4. Prompt injection через текст вакансий | средний | некорректное поведение генерации | Контент вакансий — данные, не инструкции; детальная защита в [AI_DESIGN.md](AI_DESIGN.md) §8 |
| R-5. Расходы на LLM превышают бюджет | средний | экономика продукта | Cost tracking per operation, выбор моделей по задачам, лимиты |
| R-6. Зависимость от одного embedding-провайдера | низкий | миграция индекса | Versioning эмбеддингов (embedding_model в БД), лёгкая перегенерация |
