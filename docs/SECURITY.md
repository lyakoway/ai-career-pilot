## 1. Модель активов и участников

| Актив | Чувствительность | Комментарий |
|---|---|---|
| Резюме-файлы, profile_facts | **высокая** | PII: ФИО, контакты, история занятости |
| application_documents | **высокая** | производные PII |
| Тексты вакансий (raw_data) | низкая/средняя | публичные данные; могут содержать контакты recruiters — считаем условно-приватными |
| Учётные данные (пароли, токены) | **критическая** | |
| Токены источников, Telegram bot token | **критическая** | шифруются в БД |
| LLM-промпты и трейсы | средняя | могут содержать фрагменты PII → маскирование перед Langfuse |

Участники: пользователь-владелец данных; внешний анонимный интернет (API/UI); источники вакансий; LLM-провайдеры; Langfuse (self-host или Cloud). Доверенные границы: собственная инфраструктура; полу-доверенные: LLM-провайдеры (получают производные данные в объёме задачи); недоверенные: контент источников, любые входы API.

## 2. Аутентификация и сессии

- Пароли: Argon2id (настройки по OWASP: m=19 MiB, t=2, p=1 — уточнить при реализации); длина 10–128 (верхний предел — защита от DoS хешированием); запрещённые списки паролей; обязательных «сложных» правил композиции нет (NIST SP 800-63B).
- Access JWT: HS256 (секрет ≥ 32 байт из env; апгрейт до RS256 при появлении второго сервиса-верификатора), TTL 15 мин, claims: `sub`, `iat`, `exp`, `jti`, `locale`.
- Refresh: **opaque** random 256-бит (формат `rt_<43 base64url символа>`, не JWT), хранится как sha256, TTL 30 дней, **ротация на каждое использование**; реюз отозванного токена → отзыв всех сессий (detector) + алерт (API: `401 token_reuse_detected`).
- **Хранение токенов на frontend:** access — только в памяти (Zustand-стор без персистентности, очищается при загрузке страницы); refresh — httpOnly + Secure + SameSite=Lax cookie `cp_refresh` (path=`/api/v1/auth`), недоступен JavaScript. localStorage/sessionStorage для токенов **запрещены**. Решение подтверждено — [ADR-020](DECISIONS.md) (Accepted).
- **CSRF для cookie-операций:** `SameSite=Lax` (cookie не уходит на cross-site POST) + **Origin/Referer validation** на `/auth/refresh` и `/auth/logout` (несовпадение с разрешённым origin или отсутствие обоих заголовков → `403`) + ротация с reuse-детекцией как третий эшелон (ADR-020).
- **Выход:** `POST /auth/logout` (access JWT) отзывает refresh-сессию; refresh читается **из cookie или тела** (браузер не может прочитать httpOnly cookie в JS); access доживает ≤ 15 мин (stateless, принято); скомпрометированный pre-logout refresh нейтрализуется reuse-детекцией.
- Лимиты: login/refresh — per-IP + per-account throttle (Redis), прогрессивная задержка.
- **Telegram-линкинг:** одноразовый код из 8 символов Crockford base32 без неоднозначных символов (~40 бит энтропии), TTL 10 минут; хранится **как sha256** в Redis (`cp:tg:link:{code_hash}` → user_id), не более 3 активных кодов пользователя, ≤ 5 попыток ввода кода, ≤ 5 генераций/час на пользователя (и per-IP); успешная привязка удаляет код и пишет `audit_events`. Бот в подтверждении показывает маскированный email аккаунта; chat_id хранится в `notification_channels`. Команды бота, меняющие данные, требуют подтверждения в Dashboard (MVP: бот read-only + переходы по ссылкам).
- Восстановление доступа: MVP — CLI/runbook владельца (single-user); email-flow — Stage SaaS.

## 3. Авторизация и multi-tenancy

1. Каждый запрос несёт `user_id` из JWT; доступ к сущности — только через `get_by_id(user_id, id)`; чужой id → **404** (не раскрываем существование).
2. Таблицы с `user_id` — см. [DATABASE.md §5](DATABASE.md): прикладная изоляция + опциональный RLS (`CP_DB_RLS_ENABLED`, policy `USING (user_id = current_setting('app.user_id')::uuid)`, `SET LOCAL` в транзакции).
3. Горизонтальная привилегия в API покрыта contract-тестами (матрица «пользователь A × данные B»).
4. **Изоляция в асинхронных задачах:** Celery-таски принимают только идентификаторы (`user_id`, id ресурсов), никогда — сами данные; репозитории в воркерах применяют те же tenant-правила, что и API; при включённом RLS воркер обязан выполнить `SET LOCAL app.user_id` в транзакции задачи.
5. **Presigned URL:** выдача — только эндпоинтом, проверившим владение (`get_by_id(user_id, id)`); TTL ≤ 15 мин; ключи содержат `users/{user_id}/...`; автоматической раздачи ссылок другим субъектам нет.
6. **Graph runs (LangGraph):** доступ к чекпоинтам — только через `copilot_runs` с проверкой `user_id` (API-слой валидирует владение application → run; воркер перед `Command(resume=...)` проверяет принадлежность run пользователю из задачи); `thread_id = copilot_runs.id` (UUIDv7 — не угадываем), но авторизация обязательна и не заменяется неугадываемостью id.
7. Роли: MVP — единственная роль `owner`; таблица ролей не заводится до SaaS-фазы (решение зафиксировано, см. [DECISIONS.md](DECISIONS.md)).

## 4. Данные в покое и передаче

| Слой | Мера |
|---|---|
| Transport | TLS везде (reverse proxy/terminator); HSTS |
| Диск БД/S3 | Шифрование дисков хостинга (облачные encrypted volumes); MinIO — включённое SSE |
| Файлы резюме | Приватный bucket, доступ только presigned URL (TTL ≤ 15 мин), ключи `users/{uid}/...` |
| Секреты в БД | `credentials_enc` — шифрование на уровне приложения: AES-256-GCM, ключ 32 байта из env (SaaS-фаза — KMS), формат `{key_id, nonce, ciphertext}` — ротация ключей добавлением нового `key_id` без перезаписи данных. Терминологическая правка аудита v1.1: это **не** envelope encryption (нет data keys) — «application-level encryption с версией ключа»; pgcrypto для этого столбца не используется |
| Пароли/токены | см. §2; нигде в логах и трейсах |
| Бэкапы | Зашифрованы; доступ — только владелец; restore-тест раз в этап (runbook Stage 8) |

## 5. Секреты и конфигурация

- Локально: `.env` (gitignored) + `.env.example` как документация ключей.
- Деплой: environment хостинга; опции на будущее: SOPS/Infisical, облачный KMS (ADR-013).
- Правила: секреты не в коде/образах/CI-логах (masking в Actions), ротация документирована (JWT secret — без даунтайма: два валидных секрета при смене), минимальные права у сервисных аккаунтов.
- Зависимости: `pip-audit`, `npm audit` в CI; Dependabot; pinned versions (lock-файлы).

## 6. Защита приложения

- Валидация: Pydantic на всех входах; лимиты размеров (upload ≤ 15 МБ; строки ≤ caps); content-type allowlist для файлов; `filename` санитизация при сохранении в S3 (ключ генерирует сервер).
- Rate limiting API: per-user token bucket (Redis) на дорогие эндпоинты (copilot, parsing) — защита бюджета; общие — Stage 8.
- CORS: только origin Dashboard; CSP для фронтенда (без inline scripts), security headers (X-Content-Type-Options, Referrer-Policy).
- Ошибки: наружу — обезличенные сообщения + `request_id`; стек-трейсы — только в логах/Sentry (Stage 8, опция).
- Внутренние эндпоинты (`/metrics`, admin) — не в публичном слушании / behind network policy.

### 6.1. Загрузка и парсинг файлов (резюме)

Загруженный файл — недоверенный бинарный ввод; защита многослойная:

| Слой | Мера |
|---|---|
| Тип файла | проверка **magic bytes**, а не только MIME от клиента: PDF — заголовок `%PDF-`; DOCX — zip-подпись `PK` + валидность OOXML парсером. Несовпадение заявленного и реального типа → `422` |
| Размер | ≤ 15 МБ на файл (до и после чтения в память) |
| Архивы (DOCX = zip) | защита от zip-bomb: лимит распакованного объёма (гипотеза 100 МБ), лимит числа записей (10k), лимит степени сжатия; превышение → `422 upload_decompression_limit` |
| Ресурсы парсера | hard time-limit таски (гипотеза 60 с), лимит памяти контейнера воркера; LLM-извлечение — отдельный этап после успешного текстового парсинга |
| Изоляция | парсинг выполняется в Celery `ai`-воркере вне процесса API; код парсинга **не выполняет сетевых запросов по любым URL/ссылкам, найденным в файле** (интеграционным тестом закрепляем отсутствие fetch в parse-пути); SaaS-фаза — выделенный worker-профиль без исходящего трафика (network policy) |
| Антивирус | вне MVP; риск принят: файлы приватны, не раздаются другим пользователям, рендерятся только как текст |

### 6.2. Рендеринг недоверенного контента (вакансии, документы)

- HTML из источников (`raw_data`) **никогда** не рендерится в frontend как есть: пользовательский интерфейс показывает только нормализованный `description_text`/документы, отрендеренные как **санитизированный Markdown** (allowlist-теги, DOMPurify; сырой HTML экранируется).
- Внешние ссылки — `rel="noopener noreferrer"`, автопереход запрещён; картинки из недоверенного контента не загружаются.
- Генерированные документы — тоже Markdown через санитайзер (LLM может скопировать HTML/скрипты из текста вакансии — это часть угрозы prompt injection, см. §7).

## 7. AI-специфичные угрозы

| Угроза | Митигция |
|---|---|
| Prompt injection через вакансии | [AI_DESIGN.md §8](AI_DESIGN.md): контент — данные в размеченном блоке, санитайзинг, structured outputs, отсутствие tool-execution, выходная фильтрация fact-checker'ом |
| Инъекция через резюме-файл | резюме загружает сам пользователь; тем не менее тот же принцип изоляции контента в extraction-промптах |
| Data leakage в LLM-промпты | в генерацию идут только подтверждённые факты, минимально необходимые; контакты/ФИО — только в документах-результатах, не в матчинг-запросах |
| Утечка PII в трейсы Langfuse | маскирование (MaskingPolicy) перед отправкой; полные тексты не пишутся ([AI_DESIGN.md §9.3](AI_DESIGN.md)) |
| Отравление справочника навыков | справочник изменяется только владельцем/админом; изменения логируются |
| Cost abuse (раздувание токенов) | лимиты токенов/вызовов на run, лимиты API |
| Adversarial-регрессии | датасет `prompt_injection` в eval-гейтах ([EVALUATION.md §4](EVALUATION.md)) |

Ограничение (зафиксировано честно): 100%-й защиты от LLM-инъекций не существует; принятый уровень риска = изоляция входа + структурный вывод + отсутствие автоматических действий + обязательный human review перед любым исходящим использованием.

## 8. Приватность (GDPR-подобные права, реализуем с MVP)

| Право | Реализация |
|---|---|
| Доступ/экспорт | `POST /users/me/export` → архив (JSON + файлы) асинхронно; файл в S3 `users/{uid}/exports/...`, presigned TTL 24 ч, затем удаление |
| Удаление | `DELETE /users/me` → удаление **во всех хранилищах** по матрице [DATABASE.md §6](DATABASE.md): БД-каскад, S3-префикс, langgraph-чекпоинты по списку thread_id, Redis-ключи (TTL), **очереди Celery (guard-clause в задачах + отмена активных copilot-run)**, **бэкапы (по циклу ротации)**, анонимизация audit_events; Langfuse-трейсы — best-effort (self-host: удаление по user_id; Cloud — согласно возможностям инстанса) |
| Исправление | UI редактирования фактов/профиля |
| Минимизация | в LLM-задачи — минимум данных; в логи — без PII; retention в [DATABASE.md §6](DATABASE.md) |
| Переносимость | формат экспорта — открытый JSON-схема |

Пользовательские данные не передаются третьим лицам, кроме: LLM-провайдеров (в объёме генерации, по their DPA — выбрать провайдера с DPA, зафиксировать при Stage 1), Langfuse (замаскированные трейсы).

## 9. Threat model (STRIDE-lite)

| Угроза | Сценарий | Контроль |
|---|---|---|
| Spoofing | Угадывание/кража JWT | Короткий TTL, ротация refresh, throttle логина |
| Tampering | Подмена ответа источника вакансий | Контент недоверен: нормализация, structured outputs, human review материалов |
| Repudiation | «Я не отправлял отклик» | Продукт ничего не отправляет; все действия пользователя логируются с request_id |
| Information disclosure | Доступ к чужому резюме | tenant-изоляция + RLS + presigned; contract-тесты |
| DoS | Исчерпание LLM-бюджета/воркеров | Rate limits, квоты usage_records, лимиты на run |
| Elevation | Инъекция команд через поля API | Pydantic-валидация, отсутствие динамического исполнения, ORM-параметризация |

## 10. Аудит и мониторинг безопасности

- Логи: `user_id`, `request_id`, действие, ресурс, IP/UA (только auth-события) — без содержимого данных.
- События для алертов: серия 401/403 от одного IP; реюз refresh-токена; деградация источника по AuthError; всплеск расходов LLM; ошибки fact-checker'а > порога.
- Регулярный ритуал (Stage 8): ревизия секретов, восстановление из бэкапа, обновление зависимостей.

## 11. Аудит событий безопасности

Модель: таблица `audit_events` (см. [DATABASE.md §3.15](DATABASE.md)) — append-only, запись только серверным кодом (клиент не может писать аудит). Минимальный состав MVP:

| Группа | События |
|---|---|
| Auth | `login.success`, `login.failed`, `refresh.rotated`, `refresh.reuse_detected`, `logout`, `password.changed` |
| Каналы | `telegram.linked`, `telegram.unlinked` |
| Данные | `export.requested`, `export.ready`, `account.deleted` |
| Решения | `document.approved` (существенные действия пользователя) |
| Источники | `source.enabled/disabled` |

Поля: `actor_user_id` (null — системные), `action`, `resource_type/resource_id`, `ip`, `user_agent`, `request_id`, `context jsonb` (только идентификаторы, без PII-контента). Retention — 12 мес.; при удалении пользователя записи **сохраняются** с `actor_user_id → null` + псевдонимом (`deleted_user:{id}`): журнал — доказательство исполнения права на удаление. Используется также алертами §10 (серия `login.failed`, `refresh.reuse_detected`).

## 12. Модели развёртывания и scope: Personal MVP / SaaS-ready / SaaS

Три состояния, которые нельзя смешивать (ADR-021):

| Аспект | Personal MVP (Stage 1–7) | SaaS-ready (обеспечено архитектурой уже) | SaaS (Stage 8+) |
|---|---|---|---|
| Пользователи | один владелец; аккаунт создаётся seed-скриптом/CLI | `user_id` и изоляция во всех таблицах, файлах, задачах | публичная регистрация |
| Регистрация | **закрыта**: `CP_ALLOW_REGISTRATION=false` → `403 registration_disabled` | — | открыта; email verification |
| Восстановление доступа | runbook владельца | — | email-flow, 2FA, OAuth (FR-IDN-4) |
| Биллинг/квоты | нет: `billing.check_quota` — pass-through; `usage_records` уже пишутся | таблицы `subscriptions`/`usage_records` спроектированы | активация квот + платёжный провайдер |
| RLS | выключен (`CP_DB_RLS_ENABLED=false`) | включается флагом, без миграций | включён (defense-in-depth) |
| Сеть | закрытый деплой (localhost/VPN за TLS-прокси) | — | публичный HTTPS; WAF/anti-bot — по необходимости |

Правило: SaaS-функции не реализуются раньше своего этапа; в MVP от них остаются только данные (`user_id`) и флаги. `FR-IDN-1` (регистрация) в MVP ограничена этим флагом.

## 13. Что осознанно не делается в MVP

- OAuth-провайдеры, email-верификация, 2FA — SaaS-фаза (single-user деплой за TLS + сильный пароль).
- WAF, анти-бот — не нужны при personal-деплое; пересматривается при публичном SaaS.
- SOC2/ISO — не применимо до SaaS; структура данных (изоляция, экспорт, удаление) уже готовит почву.
- Антивирусная проверка загрузок.
