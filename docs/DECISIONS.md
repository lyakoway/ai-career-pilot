- Формат: Контекст → Решение → Последствия → Альтернативы. Статусы: `Accepted` (для Stage 0), `Proposed` (утвердить в Stage 1).

## ADR-001: Модульный монолит вместо микросервисов — Accepted

**Контекст:** Продукт стартует как personal-use; эволюция в multi-user SaaS возможна, но не гарантирована. Команда — один разработчик. Требуется быстрый цикл изменений.

**Решение:** Единое backend-приложение (FastAPI) + Celery-воркеры; внутри — модули по доменам с публичными API и правилами зависимостей ([ARCHITECTURE §4](ARCHITECTURE.md)); события — transactional outbox (ADR-015).

**Последствия:** ✚ один деплой, локальные транзакции, простая отладка. ✚ Границы модулей сохраняют возможность экстракции сервисов. ✖ Требуется дисциплина границ (код-ревью, опционально import-linter); нет технологической изоляции.

**Альтернативы:** Микросервисы (отклонено: операционная сложность без выгод на этом масштабе); Serverless (отклонено: долгие LLM-пайплайны и stateful workflow).

## ADR-002: Backend-стек — Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2 (async) + Alembic — Accepted

**Контекст:** Нужен асинхронный HTTP-фреймворк с OpenAPI из коробки; AI-экосистема — Python.

**Решение:** FastAPI; Pydantic v2 — единый слой валидации (API, DTO между модулями, схемы structured outputs LLM, состояние LangGraph). SQLAlchemy 2 async в API; sync-сессии в Celery. Alembic — единственный источник схемы.

**Последствия:** ✚ Один язык валидации на всех слоях; авто-OpenAPI для фронтенда. ✖ Два стиля DB-сессий (async/sync) — стандартизировать в core.

**Альтернативы:** Django(+DRF) — тяжёлый для API-first; Litestar — эквивалентен, меньше экосистема.

## ADR-003: PostgreSQL + pgvector — единственное хранилище данных и векторов — Accepted

**Контекст:** Объём вакансий — единицы тысяч активных записей (personal use); нужна транзакционность + векторный поиск.

**Решение:** PostgreSQL 16 с `pgvector` (HNSW, cosine); эмбеддинги в отдельной таблице `job_embeddings` с версией модели.

**Последствия:** ✚ Нет дополнительной системы; транзакции; бэкап одной системой. ✖ До сотен тысяч векторов — тюнинг; при выходе за пределы — миграция на специализированный движок не требуется дизайном (job_embeddings изолирована).

**Альтернативы:** Qdrant/Weaviate/Milvus — отклонены на этом масштабе; Elasticsearch — отклонён (двойная система ради FTS, который даёт PG).

## ADR-004: Лексический поиск — PostgreSQL FTS (ts_rank_cd) + RRF-фузия; BM25 отложен — Accepted

**Контекст:** Требование — «BM25 / PostgreSQL Full-Text Search». Важно: `ts_rank` — не BM25 (нет IDF-нормализации длины документа в полноценном виде).

**Решение:** MVP — PG FTS (`tsvector` generated column, конфиг `simple` + собственная преднормализация и словарь синонимов) + Reciprocal Rank Fusion с векторным поиском. Расширение `pg_search` (ParadeDB, BM25) — задокументированная опция Stage 7, если evaluation покажет недостаточность ранжирования.

**Последствия:** ✚ Ноль дополнительной инфраструктуры; честность о природе ранжирования зафиксирована. ✖ Возможная потребность миграции на BM25-движок позже — изолировано в retrieval-слое.

**Альтернативы:** Сразу ParadeDB pg_search — отклонено: расширение вне стандартного образа PG, выигрыш не подтверждён измерениями.

## ADR-005: LangGraph для Application Copilot — Accepted

**Контекст:** Нужен stateful многошаговый workflow: паузы на недели (вопросы пользователю), human-in-the-loop, восстановление после сбоев, циклы регенерации.

**Решение:** LangGraph + `langgraph-checkpoint-postgres` (PostgresSaver; thread_id = `copilot_runs.id`). Прерывания — `interrupt()`; продолжение — `Command(resume=...)`. Проверено по официальной документации: обе возможности стабильные. Ноды — обычные Python-функции; LangChain-цепочки не используются.

**Последствия:** ✚ Персистентность/HITL из коробки; состояние в той же PG. ✖ Зависимость от жизненного цикла LangGraph API (смягчено: тонкая обёртка построения графа в модуле `copilot`).

**Альтернативы:** Самописный стейт-движок (дублирование: чекпоинты, резюмы, ретраи); Temporal (отдельная тяжёлая система ради одного workflow).

## ADR-006: Provider abstraction для LLM; без LangChain-цепочек — Accepted

**Контекст:** Несколько провайдеров/моделей; смена модели без кода; единый учёт стоимости, трассировка, маскирование, fallback.

**Решение:** Собственный `LLMClient` (Protocol) с ролями задач (extraction/generation/fact_check/embedding/...), structured outputs (JSON schema), fallback-цепочками, записью `ai_invocations`. Прямые SDK-вызовы провайдеров в адаптерах.

**Последствия:** ✚ Полный контроль; зависимость только от LangGraph. ✖ Свой код вместо готовых абстракций (~несколько сотен строк).

**Альтернативы:** LiteLLM-прокси — приемлемая опция позже, но маскирование/учёт/трейсинг всё равно свои; LangChain — не используется принципиально (см. вводные).

## ADR-007: Celery + Redis для асинхронных задач — Accepted

**Контекст:** Нужны: расписания (beat), ретраи, приоритеты, изоляция очередей (ingestion/ai/notify), зрелость под long-running LLM-таски.

**Решение:** Celery (очереди: pipeline, ai, notify, default) + Redis как брокер; Redis также для rate limiting и кэша.

**Последствия:** ✚ Зрелость, документированность, предсказуемость. ✖ Модель «pull» вместо push-событий; протухание результатов — учитываем идемпотентностью.

**Альтернативы:** arq/dramatiq/RQ — меньше возможностей планирования/наблюдаемости; Temporal — overkill; APScheduler в процессе API — нет изоляции и ретраев.

## ADR-008: Prepare, not Send — никакой автоматической отправки откликов — Accepted

**Контекст:** Площадки борются с массовыми автооткликами (пример: закрытие API hh.ru для соискателей в 2025–2026 именно из-за этого). Этика: пользователь отвечает за то, что отправляется от его имени.

**Решение:** Система генерирует и версионирует материалы; отправка всегда ручная. Browser automation, автоотклики, обход CAPTCHA — вне продукта.

**Последствия:** ✚ Правовая/этическая чистота, trust. ✖ «Последняя миля» на пользователе — принято как фича (human review — контур качества).

## ADR-009: Источники вакансий — только официально разрешённые способы — Accepted

**Контекст:** LinkedIn/Indeed/Wellfound/Работа.ру без публичного API для нашего сценария; scraping нарушает ToS и противоречит принципам проекта.

**Решение:** Подключать только источники с официальным документированным доступом (API/RSS/публичные ATS-борды после проверки ToS). Compliance-checklist для каждого адаптера ([INTEGRATIONS §7](INTEGRATIONS.md)).

**Последствия:** ✚ Устойчивость (нет игры в кошки-мышки), юридическая чистота. ✖ Покрытие уже, чем у «агрегаторов-скреперов» — осознанный компромисс.

## ADR-010: Multi-tenancy — user_id-scoping по умолчанию + опциональный RLS — Accepted

**Контекст:** MVP single-user, но данные (резюме) чувствительны; будущее — SaaS.

**Решение:** Каждая tenant-таблица несёт `user_id`; доступ через `get_by_id(user_id, id)` (чужое → 404); PostgreSQL RLS включается флагом как defense-in-depth; глобальный каталог вакансий без user-данных.

**Последствия:** ✚ Изоляция с первого дня без затрат на инфраструктуру. ✖ RLS требует `SET LOCAL app.user_id` в транзакциях — усложнение пула соединений (документировано).

**Альтернативы:** RLS сразу как основной механизм — отклонено: усложняет отладку и воркеров; база данных на тенанта — не масштабируется для нас.

## ADR-011: Langfuse как некритичная observability-зависимость (fail-open) — Accepted

**Контекст:** Нужны трассировка LLM, версии промптов, датасеты, стоимость. Langfuse v3 self-host требует 6 контейнеров (проверено), включая ClickHouse и S3 — тяжело для personal-деплоя.

**Решение:** Все LLM-вызовы идут через обёртку: при недоступности Langfuse — вызов выполняется, трейс дропается (fail-open). Учёт стоимости/токенов — в собственной `ai_invocations` (не зависит от Langfuse). Промпты канонически в git; Langfuse Prompt Management — опционально. Деплой: Langfuse Cloud (free tier) или отдельный compose-профиль.

**Поправка (Stage 0.1, 2026-11-04, финализирована):** дефолт политики трассировки — `MaskingPolicy.STRICT`: полные тексты CV, сгенерированных документов, промптов и ответов LLM в Langfuse **не отправляются** — только метаданные (модели, токены, стоимость, хэши контента). `DEBUG_CONTENT` — только явное включение на уровне конфигурации деплоя (`CP_LLM_DEBUG_CONTENT=true`), по умолчанию `false`; допустим в personal-prod для отладки, в SaaS — только staging; при старте с включённым флагом пишется WARNING; скраббер PII работает всегда, и **секреты, токены, содержимое credentials и контактные данные не передаются даже в debug-режиме** ([AI_DESIGN.md §9.3](AI_DESIGN.md)).

**Последствия:** ✚ Продукт не падает без observability; стоимость контролируется своей таблицей. ✖ Возможна потеря трейсов при сбоях — принято.

**Альтернативы:** LangSmith — отклонён (дублирует Langfuse, отдельная экосистема); без observability — невозможно отлаживать генерацию.

## ADR-012: Файлы — S3-compatible объектное хранилище — Accepted

**Решение:** MinIO в dev, любой S3 в prod; приватные bucket'ы; presigned URL TTL ≤ 15 мин; ключи `users/{uid}/...`.

**Последствия:** ✚ Стандарт, дешевизна, готовность к масштабированию. ✖ Ещё одна система в compose — приемлемо.

**Альтернативы:** Файлы в PostgreSQL (bytea) — раздувание БД и бэкапов; локальная ФС — непереносимость.

## ADR-013: Секреты — 12-factor environment в первую очередь — Accepted

**Решение:** Секреты только через переменные окружения (`.env` локально, env хостинга в прод); секреты источников — шифрованно в БД (envelope, ключ в env); миграция на SOPS/Infisical/KMS — при SaaS-фазе без изменения кода (pydantic-settings).

**Последствия:** ✚ Просто, переносимо, нет вендор-лока. ✖ Нет автоматической ротации — рунбук на Stage 7.

## ADR-014: Первая волна интеграций — Arbeitnow, Remotive, Adzuna, HN Algolia; hh.ru — платная опция — Accepted

**Контекст:** Исходное предположение «hh.ru первым через открытый API» **не подтвердилось** (проверено 2026-11-03): публичный API соискателей закрыт с 12.2025; с 04.2026 `GET /vacancies` отдаёт 403 без авторизации; легальный доступ — платная услуга «Доступ к API hh».

**Решение:** Первые интеграции — источники с подтверждённым документированным доступом (Arbeitnow, Remotive — публичные API; Adzuna — официальный API по ключу; HN Who-is-Hiring через официальный Algolia HN Search API). hh.ru: решение о покупке доступа — за владельцем (Q-1 в PRD); до этого не подключаем. ATS-борды (Greenhouse/Lever/Ashby) — после per-company проверки ToS.

**Последствия:** ✚ Старт без юридических и технических рисков. ✖ RU-рынок в MVP покрывается хуже (карьерные страницы/ATS компаний с RU-присутствием, HN) — осознанный компромисс; пересмотр по решению Q-1.

**Альтернативы:** Ждать hh.ru — блокировка всей Stage 3; использовать неофициальные клиенты hh.ru — нарушение ADR-009.

## ADR-015: Доменные события — transactional outbox, без брокера сообщений — Accepted

**Решение:** События пишутся в `outbox_events` в транзакции издателя; диспетчер (Celery) доставляет подписчикам (at-least-once, обработчики идемпотентны).

**Поправка (Stage 0.1, 2026-11-04):** дедупликация доставки формализована: подписчики с побочными эффектами дедуплицируются естественным уникальным ключом (`notifications.dedup_key`, `uq_usage`) или записью в инбокс `event_deliveries (subscriber, event_id)` ([ARCHITECTURE.md §6.2](ARCHITECTURE.md), [DATABASE.md §3.14](DATABASE.md)).

**Последствия:** ✚ Атомарность «данные+событие»; нет Kafka/RabbitMQ. ✖ Дубли доставок — обработчики обязаны быть идемпотентными; задержка секундного порядка — приемлема.

**Альтернативы:** Прямые вызовы между модулями «назад по потоку» — циклические зависимости; LISTEN/NOTIFY — теряется при простое слушателя.

## ADR-016: Первичные ключи — UUID v7 (генерация приложением) — Accepted

**Решение:** UUIDv7 из приложения: упорядоченность для индексов + генерация до INSERT (знаем id до коммита — удобно для событий/S3-ключей).

**Поправка (Stage 0.1, 2026-11-04):** в Python 3.12 stdlib-генератора uuid7 нет (появился в 3.14) — используется библиотека `uuid6` (или собственная функция) с фиксацией вендор-версии; при апгрейде до Python 3.14+ возможен переход на stdlib без изменения схемы.

**Последствия:** ✖ 16 байт против bigint — принято. ✚ Нет координации генерации; keyset-пагинация естественна.

## ADR-017: Версии документов и вакансий — иммутабельные записи — Accepted

**Решение:** `application_documents` и `job_versions` — append-only; «текущая» версия — указатель/запрос, не перезапись.

**Последствия:** ✚ Аудит, откат, воспроизводимость fact-check. ✖ Хранение — управляется retention-политикой (сжатие старых версий).

## ADR-018: Frontend — React + TypeScript + Vite + TanStack Query + Zustand + Tailwind/shadcn — Accepted

**Решение:** Стек из вводных подтверждён: TanStack Query для серверного состояния (поллинг статусов async-операций), Zustand для UI-состояния, shadcn для скорости; типы — генерация из OpenAPI (без ручных типов).

**Последствия:** ✚ Быстрый MVP-развитие, типобезопасность контракта. ✖ Генерация типов — обязательный шаг CI.

**Альтернативы:** Next.js — SSR не нужен для приватного дашборда; Vue/Svelte — экосистема меньше под shadcn-подобные библиотеки.

## ADR-019: i18n — локаль пользователя; RU/EN с первого дня; язык документов следует языку вакансии — Accepted

**Решение:** Локаль в `users.locale`; тексты API-ошибок локализуются; UI — словари (ru/en); генерация документов — на языке вакансии (или выбор пользователя).

**Последствия:** ✚ Двуязычный рынок (RU+international) покрыт сразу. ✖ Постоянные издержки на словари — приняты.

## ADR-020: Хранение и транспорт токенов на клиенте — Accepted (подтверждено владельцем 2026-11-04)

**Контекст:** Access-JWT (15 мин) + opaque refresh (30 дней). SPA-дашборд; классический риск — кража токенов из localStorage при XSS.

**Решение:** Access — только в памяти (Zustand без персистентности). Refresh — httpOnly + Secure + SameSite=Lax cookie `cp_refresh` с `path=/api/v1/auth` (недоступен JS, уходит только на auth-эндпоинты); тело ответа токен не содержит. Не-браузерные клиенты (CLI/тесты) передают refresh в теле `refreshToken`.

Подтверждённые детали (финализация Stage 0.1):

- **CSRF-защита (эшелонированная):** ① `SameSite=Lax` — cookie не отправляется на cross-site POST; ② **Origin/Referer validation** — все cookie-аутентифицированные операции (`/auth/refresh`, `/auth/logout`) проверяют заголовок `Origin` (fallback `Referer`) против разрешённого origin из конфигурации; несовпадение/отсутствие → `403`; ③ смена состояния по refresh (ротация) не даёт атакующему выгоды: ротация + **reuse detection** (реюз отозванного токена → отзыв всех сессий, `401 token_reuse_detected`) делают украденный refresh бесполезным после первого легитимного использования.
- **Logout-семантика:** `POST /auth/logout` (access JWT) отзывает refresh-сессию; refresh берётся **из cookie или тела** (браузер не может прочитать cookie в JS — тело необязательно); access-JWT остаётся валиден ≤ 15 мин (stateless, принято). Reuse-detection покрывает скомпрометированный pre-logout refresh.

**Последствия:** ✚ XSS не даёт устойчивого доступа (украденный access живёт ≤ 15 мин, refresh недоступен JS). ✖ Требование same-origin/проксирования `/api`; чуть сложнее отладка (CLI-режим оставлен). ✖ Cookie на поддоменах — учесть при SaaS-доменах.

**Альтернативы:** refresh в localStorage в теле ответа — отклонено (XSS); refresh в теле + память — эквивалент localStorage по риску; отдельный auth-сервис с BFF — избыточно для монолита.

## ADR-021: Режимы развёртывания Personal MVP / SaaS-ready / SaaS — Accepted

**Контекст:** Продукт стартует как personal-use, архитектура готовится к SaaS. Риск: смешивание скоупов — преждевременная реализация SaaS-функций (регистрация, биллинг, 2FA) усложняет MVP; или, наоборот, отсутствие изоляции в MVP заблокирует SaaS.

**Решение:** Три зафиксированных режима ([SECURITY.md §12](SECURITY.md)): Personal MVP — один владелец, seed-аккаунт, регистрация закрыта `CP_ALLOW_REGISTRATION=false` → `403 registration_disabled`, биллинг pass-through (usage_records пишутся), RLS выключен; SaaS-ready — `user_id`-изоляция во всех таблицах/файлах/задачах с первого дня, функции включаются флагами; SaaS (Stage 8) — публичная регистрация, email verification, 2FA/OAuth, квоты и платёжный провайдер, RLS включён. SaaS-функции не реализуются раньше своего этапа; в MVP от них — только данные и флаги.

**Последствия:** ✚ Явные границы скоупа для roadmap и ревью. ✖ Издержки дисциплины (флаги, изоляция) в single-user MVP — приняты как цена эволюции.
